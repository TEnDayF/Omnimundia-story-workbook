# 访谈与决策记录

## 从已有信息继续

用户可能只有一句“一个靠记忆施法的世界”，也可能提供完整设定表。先提取已有内容，选择一个会影响后续设计的缺口提问。例如：

“施法消耗的记忆会永久消失，还是可以恢复？我建议先确定这个，因为它会影响代价、治疗机制和故事的核心矛盾。”

资料中能核实的事实先查证，用户已经授权自主设计的部分直接完成；尚未授权的主角、魔法分类、国家与结局等重要选择再询问。访谈中可先展示一小段结构化结果，再问下一个相关缺口。

## 需要覆盖的领域

按相关性进入下列领域；已经明确或不适用的不必再问。

1. 核心：玩家扮演谁、初始处境、主要冲突、希望获得什么体验、可否死亡/换主控。
2. 世界：时代、地理、能源或超自然规律、历史、阵营目标与关系、核心秘密。
3. 人物：身份、外貌、性格、动机、能力限制、关系、初始位置、动态生成方式。
4. 机制：何时需要判定、成功标准、失败代价、资源、健康/压力等必要数值、恢复与持续状态、随机性。
5. 剧情：开局选项、主线阶段、独立组织行动、前置与分支、失败路线、结束条件、定时/条件/回合触发。
6. 信息：玩家开局知道什么、词条层级、知识从哪里获得、解锁依据、未知姓名与语言如何呈现。
7. 表达：叙事人称、篇幅、分段、感官/心理/动作比例、选项字段、难度和节奏。参考第二人称与结构化风险选项，但必须容纳用户其他风格。

每个领域的完成标准是它所需的输入已确定，不是提问次数达到配额。没有商店就不问商店货币，没有回合战斗就不硬造回合状态。

## 决策存档

在项目工作目录保存 `state.json` 和必要的内容草案。`state.json` 可使用以下结构，字段根据实际内容扩展：

```json
{
  "project": "项目名",
  "mode": "interview",
  "facts": [],
  "decisions": [],
  "questions": [],
  "preserve": [],
  "coverage": {}
}
```

- facts：已知世界事实及来源（用户原文/已确认方案/明确授权的补充）。
- decisions：稳定id、提案文本、用户答案、最终设定、影响的表/属性/事件、是否覆盖旧决定。
- questions：id、问题、建议、status（pending/answered/deferred）、required（是否影响定稿）。
- preserve：作者明确保留的日期、写法、机制或争议，以及理由。
- coverage：10张表分别为pending/ready/not_needed；not_needed用于明确不需要内容的功能表，仍保留表头。
- 活动版本：记录实际目标路径、最近成功写回哈希、active_content、输出路径与统计；继续任务先核对当前文件。
- 限制与来源：记录字数口径/上限、原作与译本版本、已读取章节范围、术语映射位置、改编权限和未核实项；只填当前任务需要的内容。

“我的建议”与“用户最终设定”分别存放，应用时从最终决定构建修改清单。不要重新运行包含已否决方案的整批修改草案。

## 回答映射

- 单个问题后的“对”“你的”视为接受当前展示的建议，不要求机械重复。
- 用户“不是，X…”覆盖提案中与X矛盾的部分；继承无冲突且明确指向的部分。
- 批量问答用稳定编号；收到连续简短回答时逐项对照并简述映射。若回答数少于问题数或某项两义，只追问未能映射的部分，不让其他已确认项失效。
- 用户要求一次列全时列出当前全部剩余实质问题，区分明确矛盾、可并存但需澄清、可选润色。不要把建议性的文风选择说成错误。
- 同一名称的正字以用户明确选择为准；非中文二创的译名按[来源与译名](source-localization.md)核对，原名与中文别名分开记录。

## 矛盾问题的表达

每项呈现“位置/两种描述/具体影响/最小建议”。例如：

“完成北区目标要求追踪者死亡，但后续事件要求它活着到达南区。我建议北区完成只要求它离开且装置部署完成，保留南区剧情。你希望这样改，还是保留死亡条件并调整后续？”

常规文件操作和已批准内容的同步修改不需要反复确认。若用户要求结束访谈并定稿，而仍有未授权的关键设定，给出明确待定项和可选收束方案；没有关键缺口则直接交付。
