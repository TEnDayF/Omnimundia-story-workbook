# 写法与参考样本

## 随包原创示例

先查看用户从 Omnimundia 自行导出的模板结构，再阅读下方原创 JSON 写法示例。仓库不提供 Excel 模板。
示例源文本在 [JSON](../examples/rain-lantern.json)，设计说明与路线核验在 [示例说明](../examples/README.md)。
它示范可变状态、固定知识、隐藏后台和条件剧情；随机机制、持续状态、循环事件及预设行动保留表头。
示例没有经过平台导入或真实试玩，不代表任何平台的运行承诺。

## 通用写法

1. **定义带边界**：说明是什么、如何触发、影响什么、何时结束、什么情况例外。能力描述包含对象、距离/接触条件、持续条件、成本、上限，具体数值由作者决定。
2. **事件带因果**：先写结果，再写触发条件；“完成某前置+人物存活+抵达地点”与纯日期事件分开理解。
3. **状态带更新**：属性初始值负责开局状态；规则列负责何时变化。显示知识与真实状态不是同一件事。
4. **知识有层级与来源**：名称 → 固定定义 → 性质/影响 → 获取条件。使用全角空格和┝表达父子结构，多个父项可各自从顺序1开始。未知词条在接触相关信息后解锁；健康、关系、库存等当前状态放实体，不更新进词条正文。
5. **正文与选项各司其职**：正文以当前可感知的动作、对话与反应推进，选项只给简洁行动意图，不预写结果或暗示未来。必要风险须可察觉且有依据；成功率只用于已采用的概率机制。不默认套风险评级清单、每轮400字或固定段落比例。生成提示与截图修订读[自然叙述与认知边界](narration-and-knowledge.md)。
6. **自然语言规则也要可判断**：不必全写成公式，但“极高”“一段时间”等词若参与硬判定，要问作者是否需要门槛。可恢复资源、阻尼变化、技能例外等应避免相互抵消。

## 拆分示例（仅示意，不是新项目默认设定）

用户说：“守门人每次使用能力都会积累疲劳，太累就无法开门。”

下一步先问：疲劳是叙事状态还是数值？什么程度不能开门？如何恢复？得到答案后才写：

- 实体与属性：守门人 / 数值 / 疲劳 / 用户确认初值 / 更新与阈值规则。
- 词条库：能力体系 → 开门能力 → 使用限制；必要时另设特殊值系统 → 疲劳。
- 一次性剧情点：只有已确定“开门成功导致某故事事件”时才创建事件，不把每次能力使用都做成一次性剧情。
- 随机机制：只有存在已确认的随机成功率时才填；必然成功但消耗资源的能力不凭空掷骰。


## 不继承示例设定

借鉴信息组织方法；示例的名字、日期、行动耗时和选择结果只适用于该故事。
已有实体可在玩家实际获知后追加属性，固定知识采用预编词条解锁，具体约束见 [表格结构](workbook-schema.md)。
